title: "Provenance and history"
description: "Trace any output back to the guidelines, passages, and tool calls behind it — and undo any change px0 or you have made."
---

px0 keeps its own history rather than relying on git, so a store works as a bare directory with nothing installed alongside it. Everything below works offline, on a store you just copied from another machine.

There are two granularities, and picking the right one saves you a lot of scrolling:

- **Claim level** — one section of one guideline. Use it when a single convention changed.
- **File level** — a whole workflow, guideline, or config file. Use it when you want to see an edit as a unit.

## Ask why

The question that matters most is usually "why did it say that?" There are two entry points, and they walk the same chain from different ends:

```bash
px0 runs why <run-id>       # why this output came out this way
px0 guidelines why <claim-id>   # why this convention says what it says
```

`why` walks the full chain: which guideline versions were inlined, which knowledge passages were retrieved, which tools were called, and what evidence justified any guideline change made along the way.

Use the run id when you have an output you are unhappy with. Use the claim id when you have found the rule and want to know where it came from.

## Claim-level history

Every guideline section is addressed as `<path>#<heading-slug>`. Because guideline files are versioned, one claim's history can be walked without the noise of the rest of the file:

```bash
px0 guidelines log guidelines/commit-messages.md#imperative-mood
px0 guidelines revert guidelines/commit-messages.md#imperative-mood --to v3
```

`log` prints when the section first appeared, every version that changed it, and the evidence behind each change.

`revert` restores just that section to an older version, producing a new file version that combines the old section with the current everything-else. Your other conventions are untouched — which is the whole reason claim-level addressing exists.

### When the same idea got two names

If a convention was captured once as `#imperative-mood` and later as `#use-imperative-verbs`, you have two histories for one rule. Link them rather than losing one:

```bash
px0 guidelines alias list
px0 guidelines alias link <old-claim-id> <new-claim-id>
px0 guidelines alias unlink <old-claim-id>
```

## File-level history

Any versioned file — workflows, guidelines, `config.toml` — has a full history:

```bash
px0 versions list workflows/post-standup.md
px0 versions show workflows/post-standup.md@v2
px0 versions diff workflows/post-standup.md 2 3
px0 versions revert workflows/post-standup.md --to 2
```

This includes **your** hand edits. The daemon's nightly pass checkpoints anything you changed in an editor, and a run checkpoints the workflow it is about to execute, so your edits appear in the same history as px0's rather than silently overwriting a recorded version.

```bash
px0 versions prune              # apply the version cap
px0 versions prune --dry-run    # see what it would remove first
```

Pruning only does something when `versions.keep_all` is `false`, at which point `versions.max_versions_per_file` (default `200`) applies. The default keeps everything, because Markdown files are small and the history is the point.

## The store-wide log

`changes` is the same information organized by *event* rather than by file — one entry per change, newest first, across workflows, guidelines, and config:

```bash
px0 changes list
px0 changes list --since 7d
px0 changes list --actor builder
px0 changes show <change-id>
px0 changes revert <change-id>
```

This is the view you want for "what happened to my store last week?" A single change can span several files — a workflow build that also wrote a new guideline, for instance — and `changes revert` undoes the whole thing as one unit, which is exactly what you want when a build went sideways.

## Which command do I want?

| You want to | Command |
| :--- | :--- |
| Understand an output you disagree with | `px0 runs why <run-id>` |
| Understand where a rule came from | `px0 guidelines why <claim-id>` |
| See how one convention evolved | `px0 guidelines log <path>#<anchor>` |
| Undo one convention | `px0 guidelines revert <path>#<anchor> --to vN` |
| See every version of a file | `px0 versions list <path>` |
| Compare two versions of a file | `px0 versions diff <path> <v1> <v2>` |
| Undo a whole file | `px0 versions revert <path> --to N` |
| See everything that happened recently | `px0 changes list --since 7d` |
| Undo one change across all its files | `px0 changes revert <change-id>` |

## What is not versioned

`knowledge/` and `output/` are not versioned, on purpose. Knowledge is bulk reference material, rebuildable from its source URL; output is a product of a run, and the run record already says how it was made. Version history for either would be noise you have to scroll past to find the history that matters.
