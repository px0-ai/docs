---
title: "Reviewing proposals"
description: "How px0 suggests changes to your conventions, and how you accept, edit, or dismiss them without ever losing control of the files."
---

px0 pays attention to two things: what you read, and how you edit what it produces. When either turns up something that looks like a rule — or a correction to a rule you already have — it files a **proposal**.

A proposal is not a change. Nothing under `guidelines/` is written until you say so.

## Review what is pending

```bash
px0 guidelines review
```

Each proposal shows you four things:

| Shown | Why it is there |
| :--- | :--- |
| The target file | Which convention this would change |
| The claim | The rule, in one line |
| The proposed body | The exact text that would be written |
| The evidence | `path#anchor` references behind it |

The evidence is the part worth reading. A proposal derived from something you actually wrote is very different from one derived from a blog post you skimmed, and the references tell you which you are looking at.

For each proposal you choose:

- **accept** — write it as proposed.
- **edit** — type a replacement body, and that is what gets written.
- **dismiss** — delete the pending proposal. It leaves no trace, and nothing is written.

**edit** is usually the right answer. px0 is good at noticing that a convention exists and mediocre at phrasing it the way you would.

To read what is pending without being prompted — in a script, or just to skim:

```bash
px0 guidelines review --list-only
```

## Consolidate periodically

`consolidate` is a wider sweep than `review`. Every few weeks is plenty.

```bash
px0 guidelines consolidate
px0 guidelines consolidate --list-only
```

It surfaces the same pending proposals, plus three things `review` does not:

| Also surfaced | Why it matters |
| :--- | :--- |
| **Decayed claims** | Rules that have not been reinforced in a long time. Possibly stale, possibly just settled. |
| **Contradictions** | Two guidelines that disagree. The model has to pick one, and it will not tell you it did. |
| **Unreferenced files** | Guidelines no workflow lists. They cost nothing, but they are also doing nothing. |

It ends with the same accept / edit / dismiss loop as `review`.

`proposals.max_per_consolidation` (default `10`) caps how many proposals one session surfaces, so a long-neglected store gives you a reviewable batch rather than fifty decisions in a row.

<Note>
  A freshly initialized store reports every starter guideline as unreferenced, because no workflow lists them yet. `px0 doctor` shows this as informational, never a failure — it is expected, not a fault.
</Note>

## Where proposals live

Pending proposals sit in `.state/proposals/` until you resolve them. They survive restarts, so you can walk away from a review session and pick it up later.

## Accepted changes are versioned

Accepting or editing a proposal writes a new version of the guideline file, with the evidence recorded alongside it. That is what makes the next question answerable:

```bash
px0 guidelines log guidelines/commit-messages.md#imperative-mood
px0 guidelines why <claim-id>
```

Both print not just what changed but *why* — the evidence that justified it. See [Provenance and history](/guidelines/provenance).

If an accepted change turns out to be wrong, reverting is one command and does not touch the rest of the file:

```bash
px0 guidelines revert guidelines/commit-messages.md#imperative-mood --to v3
```
