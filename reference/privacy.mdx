---
title: "What leaves your machine"
description: "px0 is local-first, not offline. Here is exactly which data goes where, and what you can keep from travelling at all."
---

px0 is local-first: your workflows, guidelines, knowledge, and run history are files on your disk, and there is no px0 server, account, or hosted state. But local-first is not the same as offline, and "your data is safe" is not a useful thing for documentation to say without specifics.

So here is every place data goes, and what you control.

## px0 itself sends nothing

px0 has no telemetry, no analytics, and no crash reporting. It does not phone home, and there is no account to associate anything with. The only network requests px0 makes on its own behalf are:

| Destination | When | What it carries |
| :--- | :--- | :--- |
| `pypi.org` | The weekly update check, `px0 update`, `px0 update --check` | Nothing about you — it reads the published version list |
| A URL you ingest | `px0 knowledge add <url>` | A plain fetch of that URL |
| `youtube.com` | Ingesting a video or playlist | The URL you gave it, to fetch metadata and transcripts |

Turn the update check off entirely if you would rather it never ran:

```bash
px0 config set update.check false
```

## Prompts go to your model backend

This is the significant one, and it is worth being precise about.

px0 has no model of its own. Every workflow run, every `px0 knowledge ask`, and every model pass inside `px0 workflows new` shells out to your coding agent CLI — `claude -p` by default — which sends the prompt to whichever provider that CLI is signed into.

What is in that prompt:

- The workflow body, after templating.
- Every guideline file the workflow lists, inlined verbatim.
- Every resolved input: tool results, retrieved knowledge passages, piped stdin.

In other words, the prompt is the union of the context the workflow gathered. If a workflow reads your calendar and your inbox, that content is in the prompt.

Two consequences worth internalizing:

**Your provider relationship is with the harness CLI, not px0.** px0 never asks for, stores, or transmits a provider API key. Whatever data-retention terms apply to your `claude`, `gemini`, `pi`, or `opencode` login apply here. If you need a different arrangement, change the harness rather than looking for a px0 setting.

**You can see the exact text that was sent.** Every run records its rendered prompt, and the run browser shows it:

```bash
px0 runs                 # open a run, read "rendered prompt"
px0 runs logs <run-id>   # the raw log
```

That is the ground truth. If you are unsure whether something reached the model, read the prompt rather than reasoning about it.

## Tool calls go through Composio

Every tool routes through [Composio](https://composio.dev), including the curated GitHub tools — those use Composio's authenticated proxy rather than calling GitHub directly. So a tool call carries its arguments to Composio, and Composio carries them to the app.

What that means in practice:

- **App credentials never touch your disk.** px0 holds a Composio API key and connected-account ids, not your Slack or Gmail tokens. Revoking access happens in Composio or at the provider.
- **Authorization is per app, and you drive it.** Nothing is connected until you complete a browser consent, and px0 only ever prepares authorizations for apps a workflow actually needs.
- **Write tools are surfaced everywhere.** The builder names them before generating a workflow, `--dry-run` stubs them, and `px0 runs` marks any run that used one — so "what has px0 sent on my behalf?" is an answerable question.

```bash
px0 tools list --status     # what is authorized right now
px0 runs list              # rows marked [write] touched the outside world
```

## What stays local, always

| Path | Guarantee |
| :--- | :--- |
| `knowledge/work/` | Never retrieved by `search`, `ask`, or a workflow `retrieve:` input, on either backend. It therefore never enters a prompt. |
| `guidelines/work/` | Never compiled into a skill bundle, so it cannot be carried into a repository by your coding agent. Still inlined into px0 prompts when a workflow lists it. |
| `.state/credentials.toml` | Local file, mode `0600`, checked on every `px0 doctor`. Excluded from `px0 store export`. |
| An exported store | Carries no API key: `config.toml` is exported with the Composio key blanked, and its version history is dropped so the key is not recoverable from the history blobs either. |
| Run records and logs | Written under `logs.path` on your machine. Nothing is uploaded. |

<Warning>
  `guidelines/work/` and `knowledge/work/` protect different things. Work *knowledge* never reaches a prompt at all. Work *guidelines* do reach prompts — they just never leave px0 as a compiled bundle. If a convention itself must not go to a model provider, do not put it in a guideline a workflow lists.
</Warning>

## Choosing how much travels

A few practical levers, in rough order of how much they buy you:

- **Keep sensitive material in `knowledge/work/`.** A hard exclusion is easier to reason about than a careful workflow.
- **Prefer read tools and dry runs while iterating.** `--dry-run` resolves real inputs but executes nothing outward, so you can inspect the prompt before anything is sent.
- **Use the local retrieval backend.** `retrieval.backend = local` is keyword search inside px0, with no model download and no embedding calls. The `qmd` backend runs its models locally too, so neither backend sends your library anywhere.
- **Scope the Composio key.** It needs `auth_configs` write access to prepare authorizations, but you decide which apps you ever consent to.
- **Skip the update check** with `update.check = false` if you want px0 to make no unprompted network request at all.
- **Set `connectors.ca_bundle`** on an inspected network. It applies to every outbound request px0 makes, so you get working TLS verification rather than the temptation to disable it.

## Moving or deleting your data

There is no export request to file and nothing to delete on a server, because there is no server.

```bash
px0 store export ~/px0-backup    # content and history, secrets stripped
rm -rf ~/.px0                    # gone
```

The export is deliberately safe to hand to someone else or drop into a backup: the Composio key is blanked in the exported `config.toml` and purged from the exported version history, and `.state/credentials.toml` is not copied at all.

`px0` never deletes your store for you, including on uninstall. See [The store](/reference/store).
